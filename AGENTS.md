# AGENTS.md

Инструкции для ИИ-агентов, работающих с этим репозиторием. Источник истины по продуктовым и архитектурным решениям — `ASSUMPTIONS.md`; здесь только поведение агента и чек-листы со ссылками на его разделы.

## Что это за проект

Сервис управления обзвоном (тестовое задание): очередь обзвона, приём событий провайдера телефонии по вебхукам, стриминг LLM-разбора звонка в веб-интерфейс. Стек: FastAPI + asyncpg + PostgreSQL 16 (RLS) · React 18 + TS + Vite + Tailwind · Docker Compose.

## Критичные инварианты — не нарушать никогда

1. **Контракт запуска**: `docker compose up -d` из корня → API на `:8080`, `GET /healthz` → `200`, PostgreSQL на `localhost:54329` (`postgres:postgres`), миграции применяются автоматически при старте. Отклонение = несданное задание. Любой PR проверяй этим сценарием.
2. **Фиксированная схема БД**: имена таблиц и перечисленных в ТЗ полей менять нельзя; расширение — только новыми полями и новыми таблицами (см. `ASSUMPTIONS.md` §2).
3. **Выдача контактов — только в БД**: логика `claim_next_contact` живёт в SQL-функции, HTTP-слой лишь аутентифицирует и проксирует (§8). Не выносить фильтры в код приложения.
4. **Вебхуки**: HMAC-подпись проверяется по сырому телу до любой обработки; невалидная подпись → `401`, в БД ничего не пишется. Идемпотентность и порядок — по правилам §4: дедуп по `provider_event_id`, применение только при `sequence > last_applied_sequence`, терминальные статусы односторонни, неизвестный `call_id` → буфер + `200`.
5. **Изоляция организаций**: RLS на всех tenant-таблицах; любой запрос от API — только в транзакции с `SET LOCAL app.org_id` из JWT (§7). Исключение — service-роль обработчика вебхуков. Прямой `WHERE org_id = ...` в коде не заменяет RLS.
6. **Схема результата разбора**: правится только в `packages/shared/analysis-result.schema.json`, затем `make codegen` (Pydantic для сервера, zod для клиента). Руками сгенерированные модели не править (§1, §9).
7. **Нефункциональные SLA**: claim ≤ 100 мс p95 на 2 млн контактов; вебхук ≤ 1 с p99 при 50 rps. Всё I/O в хендлерах — только async; синхронные вызовы (включая обращения к CRM) в request-path запрещены (§5, §8).

## Структура репозитория


## Чек-листы перед изменениями

- **Claim, индексы, производительность БД** → читать `ASSUMPTIONS.md` §8. По умолчанию: частичный индекс по `campaign_id`, `SKIP LOCKED`, блокировка через `contacts.locked_attempt_id`.
- **Приём вебхуков, статусная машина, дедуп** → §4 и §3. По умолчанию: событие всегда сохраняется, применение — через единый конвейер (матч → sequence-гард → терминальный гард → UPDATE → триггер).
- **Привязка `provider_call_id`** → §3. По умолчанию: endpoint `provider-link` + fallback по `data.attempt_id`; sweep буфера в той же транзакции.
- **CRM, ретраи, доступность внешних систем** → §5. По умолчанию: transactional outbox + фоновая задача; внешний HTTP никогда не вызывается из request-path.
- **Воркеры, зависшие попытки** → §6. По умолчанию: `abort` от воркера, reaper 30 мин → `failed {reason: "stale_timeout"}`.
- **JWT, роли, RLS** → §7. По умолчанию: стенд подписывает токены сам; `POST /dev/token` — только за dev-флагом.
- **Анализы, SSE, LLM-провайдер** → §9. По умолчанию: чанки пишутся в `analysis_chunks`, переподключение с `Last-Event-ID` дочитывает из БД, генерация не перезапускается.
- **Запуск, env, моки, сиды** → §10. По умолчанию: сиды только вручную (`make seed`), моки только в профиле `dev`.

## Ведение AI-USAGE.md

`AI-USAGE.md` — обязательный артефакт сдачи, оценивается вручную. Заполняется **по ходу работы**, а не в последний вечер: реконструировать по памяти запрещено.

- **Когда писать**: в том же коммите, где появился сгенерированный или существенно переписанный код. Забыл — отдельным коммитом `docs: ai-usage` сразу после.
- **Структура файла** (создан скелет, разделы дополняются):
  1. **Инструменты** — таблица: инструмент/модель → где применялся.
  2. **Принято без правок** — что сгенерировано и вошло как есть.
  3. **Переписано после генерации** — самая ценная для ревью часть: что, где (файл/модуль) и **почему** (ошибка модели, несоответствие решению из `ASSUMPTIONS.md`, производительность).
  4. **Написано вручную** — и почему именно руками (тонкие места: SQL-функция claim, триггер, sequence-гарды).
  5. **Как проверялось** — тесты, ручные сценарии, нагрузочные прогоны, моки.
  6. **Известные риски** — места сгенерированного кода, в которых уверенность ограничена.
- **Формат записи**: что → где → степень доверия → как проверено. Одна запись = один осмысленный блок работ, не каждый промпт.
- **Честность обязательна**: «вы отвечаете за поведение того, что сдали». Непроверенное не выдавать за проверенное; если агент написал и вы не разбирались — так и записать, это сигнал риска, а не провал.
- **Запрещено**: удалять записи о неудачных генерациях, если они привели к решению — путь через ошибку ценнее чистой истории.

## Правила работы

- **Коммиты атомарные, история не сквошится** — требование задания. Одна логическая часть = один коммит.
- **Миграции**: только новые пронумерованные файлы в `apps/api/migrations/`; уже применённые файлы не редактировать.
- **Секреты** — только через `.env` (`WEBHOOK_SECRET`, `JWT_SECRET`, `CRM_URL`, `PROVIDER_URL`); в коде — чтение из env, в репозитории — только `.env.example` с dev-заглушками.
- **Логи**: structlog JSON, correlation-id по правилам §11; не логировать тела с PII сверх необходимого.
- **После изменения поведения/контрактов** — в том же коммите синхронизировать `ASSUMPTIONS.md` (если решение изменилось) и `README.md` (если изменился запуск или состав реализованного).
- **Stop-хук** (`.cursor/hooks/stop.sh`): после завершения задачи автоматически прогоняет `react-doctor` (если менялись `js/tsx`) и `python-doctor` (если менялись `.py`, цель — `apps/api`, запуск через PATH или `uvx`). Находки возвращаются как followup — исправить или явно обосновать неприменимость. Обход в исключительных случаях: `SKIP_DOCTORS=1`.
- **Проверка перед сдачей**: `docker compose up -d` с чистого листа → `/healthz` 200 → прогон сценариев claim/webhook/SSE. Ручная проверка состояний фронта по `data-state`.
