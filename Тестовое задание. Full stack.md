## 1. Что это

Небольшой сервис, воспроизводящий фрагмент нашей платформы: очередь обзвона, приём событий от провайдера телефонии и один прикладной модуль на выбор.

Домен синтетический, частью нашего продукта не является — решение можно публиковать в портфолио.

Используйте любые инструменты, включая ИИ-ассистентов и агентов: это наш обычный режим работы. Единственное требование — вы отвечаете за поведение того, что сдали.

## 4. Ядро: модель данных

Стек БД — PostgreSQL 16 (Supabase допустим, но не обязателен). Имена таблиц и перечисленных полей фиксированы; всё остальное на ваше усмотрение.

**`orgs`** — `id uuid pk`, `name text`

**`campaigns`** — `id uuid pk`, `org_id uuid`, `name text`, `status text` (`draft` | `active` | `paused`)

**`contacts`** — `id uuid pk`, `org_id uuid`, `campaign_id uuid`, `phone_e164 text`, `timezone text` (идентификатор IANA), `attempts_count int`, `last_attempt_at timestamptz`, `do_not_call boolean`

**`call_attempts`** — `id uuid pk`, `org_id uuid`, `campaign_id uuid`, `contact_id uuid`, `provider_call_id text`, `status text`, `started_at timestamptz`, `ended_at timestamptz`, `outcome jsonb`

**`webhook_events`** — `id uuid pk`, `provider_event_id text`, `provider_call_id text`, `sequence bigint`, `type text`, `payload jsonb`, `received_at timestamptz`

Индексы, ограничения и дополнительные поля — на ваше усмотрение.

## 5. Ядро: выдача контактов

Воркеры-дозвонщики забирают контакты по одному. Выдача реализуется **функцией на стороне БД**, не логикой в коде приложения, и выставляется наружу как:

```
POST /rpc/claim_next_contact
Authorization: Bearer <jwt>
{ "campaign_id": "uuid" }

200 { "contact": { "id": ..., "phone_e164": ..., "attempt_id": ... } }
200 { "contact": null }        подходящих контактов нет
```

**Контакт может быть выдан, только если выполнено всё:**

1. Кампания в статусе `active`.
2. `do_not_call = false`.
3. `attempts_count < 3`.
4. Локальное время контакта (в его таймзоне) находится в интервале `[09:00, 20:00)`.
5. С момента `last_attempt_at` прошло не менее 4 часов (либо попыток ещё не было).

При выдаче создаётся запись `call_attempts` со статусом `queued`; её идентификатор возвращается как `attempt_id`.

Контакт, выданный воркеру, не выдаётся повторно, пока попытка не перешла в терминальный статус. Воркеры работают параллельно, в проде их от пяти до двадцати.

**Доступ.** JWT — HS256, claims: `sub`, `org_id`, `role`. Значение `role` равно `worker` для сервисных воркеров и `authenticated` для пользователей веб-приложения. Оба типа вызывают один и тот же эндпоинт. Организации не должны получать доступ к данным друг друга ни через API, ни напрямую через БД-роль веб-приложения.

## 6. Ядро: события провайдера

```
POST /webhooks/calls
X-Signature: sha256=<hex>

{
  "event_id": "evt_01HX...",
  "call_id": "call_01HX...",
  "sequence": 3,
  "type": "call.answered",
  "occurred_at": "2026-08-04T12:00:03.412Z",
  "data": { "sip_code": 200, "duration_sec": 0 }
}
```

`X-Signature` — HMAC-SHA256 от сырого тела запроса с ключом `WEBHOOK_SECRET`. Невалидная подпись → `401`, тело не обрабатывается.

**Типы и целевой статус `call_attempts`** (связь по `provider_call_id`):

| `type` | `status` |
|---|---|
| `call.queued` | `queued` |
| `call.dialing` | `dialing` |
| `call.answered` | `in_progress` |
| `call.completed` | `completed` |
| `call.failed` | `failed` |
| `call.no_answer` | `no_answer` |

`call.answered` заполняет `started_at`, терминальные типы — `ended_at` и `outcome` (в `outcome` кладётся объект `data` события).

**Свойства доставки.** Провайдер доставляет события at-least-once: одно и то же событие может прийти более одного раза. Повторная доставка не должна приводить к повторному применению. Поле `sequence` монотонно возрастает и уникально в пределах одного `call_id`. Провайдер считает доставку неуспешной при ответе, отличном от `2xx`, или при отсутствии ответа в течение 2 секунд, и повторяет её.

Все принятые события сохраняются в `webhook_events`.

**Побочные эффекты при переходе в терминальный статус** (`completed`, `failed`, `no_answer`) — реализуются триггером на стороне БД:

1. `contacts.attempts_count` увеличивается на единицу.
2. `contacts.last_attempt_at` устанавливается в `ended_at`.
3. Если в `outcome` присутствует поле `do_not_call` со значением `true` — выставляется `contacts.do_not_call = true`.

**Уведомление CRM.** После перехода звонка в терминальный статус во внешнюю CRM отправляется `POST` на `CRM_URL` с телом `{ "attempt_id": ..., "status": ..., "outcome": ... }`. Успехом считается ответ `2xx`.

## 6.1. Нефункциональные требования к ядру

- Таблица `contacts` в проде — до 2 млн строк. `claim_next_contact` укладывается в **100 мс p95** на таком объёме.
- `POST /webhooks/calls` отвечает не дольше **1 с p99** при нагрузке 50 rps.
- Внешняя CRM — сторонняя система с собственной доступностью; её состояние не должно влиять на приём событий от провайдера.
- Структурные логи с корреляционным идентификатором, сквозным от вебхука до записи в БД.

## 7. Разбор звонка: стриминг результата

Разбор завершённого звонка: транскрипт уходит в LLM, структурированный результат стримится в интерфейс по мере генерации.

### 7.1. Контракт вышестоящего провайдера

Провайдер доступен по `PROVIDER_URL`. Ваш стенд для разработки вы пишете сами по этому контракту; при проверке подставляется наша реализация.

```
POST {PROVIDER_URL}/v1/analyze
{ "request_id": "...", "transcript": "..." }

200, Content-Type: text/event-stream

event: chunk
data: {"field":"summary","delta":"Клиент интерес"}

event: done
data: {"result": { ... }}
```

Провайдер может ответить `429` с заголовком `Retry-After` (в секундах), оборвать соединение в середине потока или вернуть результат, не соответствующий схеме из 7.3.

### 7.2. Ваш API

```
POST /api/analyses               { "call_attempt_id": "uuid" } → { "id": "uuid", "status": "queued" }
GET  /api/analyses/:id           → текущее состояние и накопленный результат
GET  /api/analyses/:id/stream    → SSE
POST /api/analyses/:id/cancel    → отмена
```

События SSE: `chunk` (с полем `id`), `done`, `error`. Клиент, переподключающийся с заголовком `Last-Event-ID`, должен получить продолжение потока, а не его повтор и не перезапуск генерации. Все эндпоинты авторизуются JWT; чужая организация получает `404`.

### 7.3. Схема результата

Финальный результат обязан соответствовать:

```
summary     string
objections  string[]
next_step   "call_back" | "send_proposal" | "disqualify" | "escalate"
lead_score  integer 0..100
confidence  number 0..1
```

Ответственность за то, что наружу уходит валидный результат, лежит на вас. Схема должна быть единым источником истины для сервера и клиента.

### 7.4. Интерфейс

React 18 + TypeScript + Vite + TailwindCSS на `http://localhost:5173`. Одна страница: запуск разбора и живой просмотр. Состояния `queued`, `streaming`, `reconnecting`, `partial`, `error`, `cancelled` должны быть различимы в DOM — используйте атрибут `data-state` на контейнере, мы читаем его автоматически. Частичный результат при обрыве остаётся на экране.

Оформление не оценивается. Корректность состояний — оценивается.
